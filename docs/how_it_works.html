NewsPrism 동작 방식

버튼을 눌렀을 때 브라우저, 서버, 에이전트가 어떤 순서로 움직이는지 정리했습니다. 코드(app.py, graph.py, nodes/, tools/)를 기준으로 썼습니다.

브라우저화면(index.html)서버FastAPI(app.py)에이전트LLM을 호출하는 노드외부SerpApi, 구글 뉴스, 언론사 사이트캐시samples/cache 파일

구성 한눈에 보기

서버는 FastAPI 하나이고, 분석은 LangGraph로 만든 에이전트 파이프라인이 맡습니다.

API언제 호출되나LLM 사용
GET /페이지를 열 때없음
GET /api/headlines?limit=N첫 화면(5건), "더보기"(20건). 새로고침 아이콘은 &refresh=1을 붙여 캐시를 건너뜀없음
GET /api/summary/{id}주요 뉴스 카드마다 (요약 채우기)기사당 1회
GET /api/search?q=검색창에서 검색할 때없음
POST /api/jobs"여러 시선으로 보기"를 누를 때 (주요 뉴스 카드에서는 카드 id도 함께 보냄)분석 전체(약 25회 안팎)
GET /api/jobs/{id}분석 중 1.5초마다 (진행 상황 확인). 저장된 결과도 이 주소로 열린다없음
GET /api/analyses최근 분석 기록 목록없음

1. 페이지를 열었을 때자동 실행

화면이 뜨자마자 주요 뉴스 5건과 각 요약이 채워집니다.

  1. 브라우저

    GET /로 index.html을 받는다.

    글꼴(Pretendard)은 CDN에서 불러온다.

  2. 브라우저

    GET /api/headlines?limit=5를 호출한다.

  3. 캐시

    구글 뉴스 주요기사 결과가 30분 이내에 저장된 것이면 그대로 쓴다.

    30분이 지났으면 아래 단계에서 새로 받는다.

  4. 외부

    SerpApi로 구글 뉴스 주요기사를 받는다. 구글이 같은 사건 기사를 묶어서 준다.

  5. 서버

    받은 묶음을 정리한다.

    • 묶음마다 대표 기사 1건을 정하고 보도한 언론사 목록을 만든다.
    • "이 시각 헤드라인", "브리핑" 같은 종합 기사는 대표와 집계에서 뺀다.
    • 언론사 이름을 통일한다. (KBS 뉴스, KBS뉴스 → KBS)
    • 보도 언론사가 많은 사건 순으로 순위를 매긴다. 제목이 비슷한 묶음은 한 사건으로 합친다.
    • 5건이 안 되면 구글 뉴스 RSS 주요기사(10분 메모리 캐시)로 부족분을 채운다. 이쪽은 사진이 없다.
  6. 서버

    항목마다 id를 붙여 서버 메모리에 보관하고(묶음에 속한 기사 전체 포함) 목록을 돌려준다. 응답 헤더 X-Fetched-At에는 데이터를 실제로 받아 온 시각이 들어간다.

  7. 브라우저

    1순위는 큰 카드, 2~5순위는 작은 카드로 그린다. 제목 옆에 "MM/DD HH:mm 기준"(데이터를 받은 시각)을 표시하고, 요약 자리는 회색 막대로 비워 둔다.

    오른쪽의 새로고침 아이콘을 누르면 캐시를 건너뛰고 SerpApi와 RSS에서 새로 받아 온다. (누를 때마다 SerpApi 1회 사용)

  8. 브라우저

    카드마다 GET /api/summary/{id}를 호출한다. 서버 부담을 줄이려고 한 번에 4개까지만 요청한다.

  9. 캐시

    이미 만든 요약(summary_*.json)이 있으면 바로 돌려준다.

  10. 외부

    없으면 기사 원문 주소를 복원하고 본문을 내려받는다. (결과는 article_*.json에 캐시)

  11. 에이전트

    요약 에이전트가 본문을 읽고 두 문장으로 요약한다. (LLM 1회)

    본문을 못 가져온 기사(유료·차단)는 지어내지 않고 요약을 비워 두며, 이 경우 카드에서 요약 영역이 사라진다. 실패는 캐시하지 않아 다음에 다시 시도한다.

2. "더보기"를 눌렀을 때

  1. 브라우저

    전체 목록 화면으로 바꾸고 GET /api/headlines?limit=20을 호출한다. (처음 한 번만. 다시 열면 받아 둔 것을 쓴다)

  2. 서버

    1번과 같은 과정으로 최대 20건을 순위대로 만든다. 사진이 있는 구글 뉴스 묶음이 먼저, RSS로 보충한 항목이 뒤에 온다.

  3. 브라우저

    목록을 그리고 각 항목의 요약을 1번과 같은 방식(4개씩, 캐시 우선)으로 채운다.

처음 열 때는 아직 요약이 없는 항목이 많아서, 위에서부터 차례로 채워집니다. 한 번 만든 요약은 캐시에 남아 다음부터 즉시 나옵니다.

3. 오른쪽 위 돋보기로 검색했을 때

  1. 브라우저

    검색 패널을 열고, 입력 후 엔터 또는 예시 버튼을 누르면 GET /api/search?q=키워드를 호출한다.

  2. 서버

    search(q, 30)을 실행한다.

    • SerpApi 키가 있으면: 네이버 뉴스와 구글 뉴스 결과를 번갈아 섞어 30건까지 만든다.
    • 키가 없거나 실패하면: 구글 뉴스 RSS로 대신한다.
  3. 캐시

    같은 키워드는 저장된 결과를 다시 쓴다. (검색 결과는 만료 시간이 없다)

  4. 브라우저

    제목, 언론사, 몇 시간 전인지를 목록으로 보여준다. LLM은 쓰지 않는다.

4. "여러 시선으로 보기"를 눌렀을 때핵심 기능

주요 뉴스 카드, 더보기 목록, 검색 결과 중 어디서 눌러도 같습니다. 그 기사의 제목을 키워드로 삼아 분석합니다.

  1. 브라우저

    분석 화면으로 바꾸고 POST /api/jobs에 {"query": 제목}을 보낸다.

  2. 저장소

    같은 기사를 12시간 안에 이미 분석했다면(SQLite data/newsprism.db) LLM을 다시 돌리지 않고 저장된 결과를 바로 돌려준다. 결과 화면의 "다시 분석하기"는 refresh=true로 새로 분석한다.

  3. 서버

    저장된 결과가 없으면 작업 id를 만들어 작업표(JOBS)에 "진행 중"으로 올리고, 카드 id가 있으면 그 사건 묶음의 기사들을 "씨앗 기사"로 꺼내 둔 뒤 별도 스레드에서 분석을 시작한 뒤 id를 바로 돌려준다.

    그래서 분석이 1~2분 걸려도 화면이 멈추지 않는다.

  4. 브라우저

    1.5초마다 GET /api/jobs/{id}로 진행 상황을 묻고 단계 표시와 진행 막대를 갱신한다.

에이전트는 언제, 어떻게 움직이나작업 스레드 안

아래는 서버의 작업 스레드에서 LangGraph가 실행하는 순서입니다. 노드가 하나 끝날 때마다 화면의 진행 단계가 바뀝니다.

  1. 1단계

    기사 수집 (collect_articles) · 화면 표시: "기사 수집"

    • 후보를 모은다: ① 카드에서 시작했다면 구글이 이미 같은 사건으로 묶어 둔 기사(씨앗 기사) ② 말머리([속보])와 따옴표를 뺀 제목으로 검색한 40건.
    • 모인 언론사가 5곳 미만이면 LLM이 짧은 검색어 2~3개를 만들어 추가로 검색한다. (LLM 1회, 조건부) 만든 검색어는 파일에 저장해 같은 기사에는 다시 쓴다.
    • 언론사마다 사건과 제목이 가장 비슷한 기사 1건을 고른 뒤, 최대 12곳을 중요도 순으로 고른다. 우선순위는 ① 카드가 묶어 준 언론사 ② 제목이 사건과 비슷한 기사 ③ 주요 언론사(종합지·방송·주요 경제지) ④ 제목 유사도이다.
    • 10건의 원문 주소를 복원하고 본문을 동시에 내려받는다. (캐시에 있으면 건너뜀)
    • LLM 1회: 제목들을 보고 가장 많이 다뤄진 하나의 사건을 "기준 사건"으로 정한다.
  2. 2단계

    주제 판정 (judge_topic) · "같은 주제 판정"

    • 기사 수만큼 동시에 실행된다. (10건이면 LLM 10회 병렬)
    • 각 기사가 기준 사건과 같은 사건인지 "예/아니오"와 근거를 낸다.
  3. 3단계

    기사 거르기 (filter_articles) · 코드

    • "예"인 기사만 남긴다.
    • 남은 기사가 2건 미만이면 분석을 접고 "비교할 수 없다" 안내(no_report)로 끝낸다.
  4. 단독 보도

    같은 주제 기사가 정확히 1건이고 본문이 있으면 4~7단계 대신 아래 경로로 간다. (화면의 진행 단계도 바뀐다)

    • single_factcheck: 핵심 주장 6~10개와 근거 문장, 출처 유형을 뽑고 근거 문장이 본문에 있는지 코드로 확인한다. (LLM 1회)
    • single_research: 검색어로 다른 언론사 관련 기사를 최대 8건 찾아 본문을 가져오고, 주장마다 교차 확인됨 / 일부 확인 / 확인 불가 / 다른 정보 있음으로 나눈다. 판정마다 그 기사에서 가져온 문장을 붙이고, 인용문이 자료에 실제로 없으면 인정하지 않는다. 배경과 다른 관점도 함께 고른다. (LLM 1회 + 뉴스 검색)
    • write_single: 보도 내용, 교차 확인 결과, 배경과 맥락, 다른 관점, 함께 생각해 볼 점으로 새 요약 기사를 쓴다. 원 기사가 틀렸다고 판정하지 않고 모든 문장에 출처를 밝힌다. 단독 보도라는 안내는 코드가 따로 붙인다. (LLM 1회)
    • check_single: 원문 근거와 표현·출처 표기를 검사한다. 통과하지 못하면 다시 쓴다(최대 2회). (LLM 2회 동시)
    • 결과 화면은 새 기사, 팩트체크(판정과 인용), 배경과 다른 관점, 참고한 기사, 검증 순서로 보인다. 외부 자료가 뉴스 검색 결과에 한정된다는 점도 함께 표시한다.
  5. 4단계

    기사별 분석 (analyze_article) · "기사별 분석"

    • 남은 기사 수만큼 동시에 실행된다. (LLM 기사당 1회)
    • 핵심 주장, 강조한 사실과 근거 문장, 인용 출처, 어조를 뽑는다.
    • 근거 문장이 본문에 글자 그대로 없으면 코드가 버린다.
  6. 5단계

    비교 (compare_articles) · "비교"

    • 모든 분석을 한 번에 넣고 LLM 1회로 공통 사실, 주요 쟁점(누가 어떤 입장인지), 질문을 만든다.
    • 과반 미만이 보도한 "공통 사실"은 코드가 "일부만 다룬 내용"으로 내린다.
  7. 6단계

    중립 요약 (write_summary) · "중립 요약 작성"

    • 비교 결과로 5문장 이내 요약을 쓴다. (LLM 1회) 다시 쓰는 경우에는 검증이 지적한 문제를 함께 받는다.
  8. 7단계

    팩트·편향 검증 (check_bias) · "팩트·편향 검증"

    • LLM 2회를 동시에: 요약을 주장 단위로 쪼개 기사에 근거가 있는지 확인하고, 평가·감정 표현과 한쪽 편중을 채점한다.
    • 통과하면 8단계로. 통과하지 못하면 6단계로 돌아가 다시 쓴다.
    • 다시 쓰기는 최대 2회까지이고, 그래도 통과하지 못하면 미통과 표시를 붙인 채 내보낸다.
  9. 8단계

    리포트 조립 (build_report) · "리포트 조립" · 코드

    • 결과를 하나로 묶는다. 서버는 작업표의 상태를 "완료"로 바꾸고 결과를 저장한다.
  10. 브라우저

    다음 확인 때 "완료"를 받으면 진행 화면을 닫고 결과를 그린다.

    • 한눈에 보기, 모두가 전한 사실, 주요 쟁점, 함께 생각해 봐요, 비교한 기사, 중립성 검증
LLM 호출 횟수(기사 10건 기준): 기준 사건 1 + 주제 판정 10 + 기사별 분석 최대 10 + 비교 1 + 요약 1 + 검증 2 = 약 25회. 검증에 실패해 다시 쓸 때마다 (요약 1 + 검증 2)가 더해집니다.

5. 분야(카테고리) 탭을 눌렀을 때

주요 탭을 제외한 7개 탭(정치, 경제, 사회, 세계, IT·과학, 생활·문화, 스포츠)은 하루에 한 번 만든 목록을 보여줍니다.

  1. 브라우저

    GET /api/headlines?category=분야를 호출한다. 새로고침 아이콘은 주요 탭에서만 보이고, 서버도 다른 분야의 새로고침 요청은 무시한다.

  2. 캐시

    오늘 날짜의 cat_분야_날짜.json이 있으면 그대로 돌려준다.

  3. 외부

    없으면(그날 첫 요청이거나 서버가 막 켜졌을 때) 구글 뉴스 8개 섹션 RSS에서 섹션마다 상위 40건씩 가져와, 제목이 비슷한 기사는 하나로 합친다.

  4. 분류

    LLM이 약 230건을 60건씩 묶어 4회 동시에 분류한다. 구글이 붙인 분야는 힌트로만 쓰고, 세계·스포츠 섹션은 그대로 확정한다.

    • 기사마다 주 분야 1개와, 중심 내용이 다른 분야에도 실제로 걸칠 때만 부 분야 1개를 정한다.
    • 국내 기사에 "대통령", "국회" 같은 명백한 정치 단어가 있으면 코드가 정치로 확정한다.
    • 각 분야 목록은 상위 5건이 주 분야 기사만이고, 6번째부터 부 분야로 걸린 기사가 중요도 순으로 섞인다. 카드에는 "세계 · 경제"처럼 분야 표시가 붙는다.
  5. 외부

    저장하는 20건에 원문 주소와 대표 사진(og:image)을 채운다. (결과는 thumb_*.json에 캐시)

  6. 서버

    서버가 켜지면 백그라운드 작업이 7개 분야를 미리 만들고 상위 5건의 요약도 만들어 둔다. 30분마다 날짜가 바뀌었는지 확인한다.

처리 시간과 안정성을 위한 구조

LLM 서비스가 간헐적으로 80~100초씩 멈추는 것이 측정되어(정상 호출은 3초 안팎), 아래와 같이 대응합니다. 서비스 상태에 따라 분석 시간은 1~3분 사이에서 크게 달라질 수 있습니다.

대응내용
멈춘 호출 재요청llm.py: 요청 크기에 따라 6~30초 안에 응답이 없으면 같은 요청을 한 번 더 보내 먼저 오는 쪽을 쓴다. 실패하면 최대 3회까지 다시 시도하고, 130초가 넘으면 포기한다.
판정과 분석을 동시에process_article: 기사 1건의 "같은 사건인지 판정"과 "기사별 분석"을 동시에 실행해 LLM 단계 하나를 없앤다. 판정에서 제외된 기사의 분석은 버려진다.
기준 사건 생략주요 사건 카드에서 시작한 분석은 헤드라인을 기준 사건으로 그대로 써서 LLM 호출 하나를 아낀다.
기사 하나의 실패 허용기사 하나의 판정·분석이 끝내 실패하거나 응답을 해석하지 못해도 전체 분석은 계속한다. (그 기사만 제외)
재작성 줄이기검증이 "근거 없는 문장"이나 "틀린 언론사 이름"만 지적한 경우, LLM으로 요약을 다시 쓰지 않고 코드가 그 문장·이름을 빼서 바로 통과시킨다. 고친 내용은 결과 화면에 표시한다. 재작성 1라운드는 요약과 검증을 합쳐 40~60초가 든다.
정확한 재작성 지시검증이 "어느 언론사 표기가 틀렸고 근거가 확인된 언론사는 어디인지"까지 알려 준다. 인용문 비교는 물결표·따옴표·공백 차이를 같은 문장으로 본다.
